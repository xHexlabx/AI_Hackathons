# Road Users Detection 🛣️

> Kaggle: <https://www.kaggle.com/competitions/th-road-safety> · SuperAI SS4 InClass (TrafficHackathon, ก.ค. 2024) · เริ่มทำใหม่ 2026-09-12

ตรวจจับผู้ใช้ถนน 11 ประเภทจากภาพกล้องจราจรในประเทศไทย รอบนี้ตั้งใจ **เทรนโมเดลเอง** ด้วยโมเดลตระกูล DETR ที่ทำนายเป็นเซ็ตและไม่ต้องใช้ NMS

> **Task** : Object Detection (11 คลาส) &nbsp;|&nbsp; **Metric** : mAP &nbsp;|&nbsp; **Tools** : DETR family (เป้าหมาย Co-DETR) &nbsp;|&nbsp; **Status** : 🔥 กำลังทำ

## 🎯 โจทย์

| | |
|---|---|
| **Input** | ภาพนิ่งจากกล้องจราจร `.jpg` ขนาด 1920 × 1080 ทุกภาพ |
| **Output** | กล่อง `[x1, y1, x2, y2]` เป็นพิกเซล + class id + confidence ต่อภาพ |
| **คลาส** | `pedestrian` `bicycle` `motorcycle` `car` `taxi` `van` `truck` `bus` `emergency_car` `tuktuk` `other` (id 0–10) |
| **Label** | YOLO `.txt` ต่อภาพ (`class cx cy w h` แบบ normalized) |
| **Metric** | Mean Average Precision (mAP) เฉลี่ยรายคลาส |
| **ส่งได้อยู่** | แม้ปิดไปแล้ว ยังส่ง late submission ได้ วันละ 100 ครั้ง และได้ทั้ง public และ private score |
| **รอบเดิม** | 5–7 ก.ค. 2024 · ทีมละ 3 คน · ส่งได้ 4 ครั้ง/วัน · test แบ่ง public/private 50/50 |
| **Leaderboard เดิม** | อันดับ 1 ได้ 0.75583 · อันดับ 5 ได้ 0.67714 |

Submission เป็น 1 แถวต่อ 1 ภาพ คอลัมน์ `id,boxes,labels,scores` โดย 3 คอลัมน์หลังเป็น list ที่ stringify มา และปล่อยว่างได้ถ้าภาพนั้นไม่เจออะไรเลย

```csv
id,boxes,labels,scores
TF7-KS-1-01-28032023(12.00-13.00)_1304.jpg,"[[1730, 283, 1755, 328], [1196, 107, 1236, 133]]","[0, 3]","[0.24, 0.73]"
TF4-DS-12-02-28032023(12.00-13.00)_645.jpg,,,
```

> ⚠️ **กับดัก: แถวว่างทำให้ scorer ขึ้น ERROR** ทั้งที่ `sample_submission.csv` ของผู้จัดเองมีแถวว่างเป็นตัวอย่าง
> ทดสอบแล้วเมื่อ 2026-09-13 ไฟล์ที่มีแถวว่างแค่ 2 แถวจาก 1,407 ก็ ERROR ทันที ส่วนไฟล์เดียวกันที่บังคับให้ทุกภาพมีอย่างน้อย 1 กล่องผ่านปกติ
> `predict.py` จึงใส่กล่องจิ๋วความมั่นใจ 0 ให้ภาพที่ไม่เจออะไรเลย

> ⚠️ mAP เฉลี่ยรายคลาส แปลว่า **`emergency_car` ที่มี 31 กล่องทั้ง dataset มีน้ำหนักเท่ากับ `motorcycle` ที่มี 7,114 กล่อง**
> ทุกการตัดสินใจหลังจากนี้ต้องเช็กว่ามันทำอะไรกับคลาสหายาก ไม่ใช่ดูแค่คะแนนรวม

## 🔍 สิ่งที่ EDA บอก

รันด้วย [`scripts/eda.py`](scripts/eda.py) — สามอย่างนี้เปลี่ยนลำดับความสำคัญของงานไปจากที่คิดไว้ตอนแรก

### 1. ภาพ train 62% ยังไม่มี label — และนั่นคือส่วนหนึ่งของโจทย์

1,605 ภาพมี label ส่วนอีก **2,621 ภาพไม่มีไฟล์ `.txt` เลย** และ **ไม่มีไฟล์ label ว่างเปล่าแม้แต่ไฟล์เดียว** ถ้าภาพเหล่านั้นคือฉากที่ไม่มีวัตถุ ควรมี `.txt` ว่างโผล่มาบ้าง เมื่อไม่มีเลยแปลว่ามันคือภาพที่ยังไม่ถูก annotate

หน้า overview ยืนยันตรง ๆ ว่าตั้งใจให้เป็นแบบนั้น

> *"The dataset does not provide annotations, participants must create their own annotations as part of the competition task."*

แปลว่า **การ annotate เป็นงานที่ผู้จัดตั้งใจให้ทำ ไม่ใช่ทางลัด** การลงทุนทำ auto-labelling loop ที่ดีจึงเป็นเส้นทางหลักของโจทย์นี้ ไม่ใช่ของแถม และมีภาพให้ใช้มากกว่า label ที่มีอยู่ 1.6 เท่า

### 2. วัตถุเล็กมาก และแน่นมาก

| | |
|---|---|
| วัตถุทั้งหมด | 19,862 กล่อง |
| ต่อภาพ | เฉลี่ย 12.4 · median 6 · มากสุด 76 |

| วัตถุที่เล็กกว่า 0.1% ของภาพ | 7,652 กล่อง (38.5%) |

เกือบ 4 ใน 10 ของวัตถุเล็กกว่า ~45 × 45 px บนภาพ 1920 × 1080 นี่คือปัญหาที่ใหญ่ที่สุดของโจทย์ และมันแก้ด้วย **ความละเอียดภาพเข้าโมเดล + multi-scale feature** ไม่ใช่ด้วยการเปลี่ยนสถาปัตยกรรม

## 🎞️ ภาพมาจากวิดีโอ ไม่ใช่ภาพเดี่ยว

ชื่อไฟล์มีเลขเฟรมต่อท้าย เช่น `TF4-DS-09-01-28032023_630.jpg` แกะด้วย [`scripts/sequence_check.py`](scripts/sequence_check.py) แล้วได้ภาพที่เปลี่ยนแผนหลายข้อ

| | train | test |
|---|---|---|
| ภาพ | 4,226 | 1,407 |
| เซสชันกล้อง | 24 | 24 |
| ระยะห่างระหว่างเฟรม | 1–4 เฟรม (แน่น) | **5 เฟรมเป๊ะ** 1,377 จาก 1,406 ช่วง |

**ทั้ง 24 เซสชันถูกใช้ทั้งใน train และ test** ไม่มีกล้องไหนถูกกันไว้เป็น held-out เลย แต่แบ่งกันด้วย *ช่วงเวลา* ภายในเซสชัน ระยะจากเฟรม test ไปเฟรม train ที่ใกล้ที่สุดมี median 146 เฟรม และมีแค่ 5.9% ที่ห่างไม่เกิน 5 เฟรม

### 1. วิธีแบ่ง validation ที่ถูกต้องมีแบบเดียว

ที่สำคัญกว่านั้น **test คือช่วงท้ายของแต่ละเซสชัน** 19 จาก 24 เซสชันมีเฟรม test อยู่หลังเฟรม train ตัวสุดท้ายทั้งหมด ที่เหลืออีก 5 เซสชันแทรกกันแค่ 4–34%

- **สุ่มแบ่งรายภาพ = รั่วหนัก** เฟรม train ห่างกันแค่ 1–4 เฟรม ภาพข้าง ๆ กันแทบเป็นภาพเดียวกัน validation จะสวยเกินจริงมาก
- **แบ่งตามกล้อง = โหดเกินจริง** เพราะ test ใช้กล้องชุดเดียวกับ train ครบทั้ง 24 ตัว การกันกล้องออกคือจำลองโจทย์ที่ยากกว่าของจริง จะเลือกโมเดลผิด
- **ที่ถูกคือกันเป็นบล็อกเวลาต่อเนื่องออกจากทุกเซสชัน** ทำไว้แล้วใน [`scripts/make_split.py`](scripts/make_split.py)

### 2. จำนวนภาพที่ "เป็นอิสระจริง" น้อยกว่า 1,605 มาก

เฟรมที่ห่างกัน 1–4 เฟรมนับเป็นตัวอย่างเดียวกันเกือบหมด ตอนคิด augmentation กับ schedule ต้องมองที่จำนวนฉากจริง ไม่ใช่จำนวนไฟล์

### 3. การ annotate ที่เหลือง่ายกว่าที่คิดมาก

เฟรมที่ยังไม่มี label 2,621 ภาพ อยู่ใกล้เฟรมที่มี label แค่ไหน

| ห่างไม่เกิน | สัดส่วน |
|---|---|
| 1 เฟรม | 19.5% |
| 3 เฟรม | 47.5% |
| 5 เฟรม | 65.6% |
| 10 เฟรม | **89.4%** |

เกือบ 90% ของเฟรมที่ยังไม่มี label อยู่ห่างเฟรมที่มี label ไม่เกิน 10 เฟรม ระยะแค่นี้วัตถุแทบไม่ขยับ การ **propagate label ด้วย tracker หรือ optical flow** จึงแม่นกว่าการ pseudo-label ด้วยโมเดลแบบมองภาพเดี่ยว ๆ เยอะ และยังได้ label ที่สอดคล้องกันข้ามเฟรมเป็นของแถม

### 4. test ก็เป็นลำดับเฟรม จึงใช้เวลาเป็นตัวช่วยได้

เฟรม test ในเซสชันเดียวกันเรียงต่อกันทุก 5 เฟรม แปลว่า detect ทีละภาพแล้ว **เชื่อมด้วย tracker ข้ามเฟรมเพื่อกู้วัตถุที่หลุด** ได้ และตรงนี้แหละที่แก้ปัญหาการบังกันได้จริง รถที่ถูกบังมิดในเฟรมหนึ่ง มักโผล่ชัดในเฟรมก่อนหน้า 5 เฟรม ซึ่งเป็นข้อมูลที่โมเดลมองภาพเดี่ยวไม่มีวันเห็น

## ✂️ Validation split

`uv run python scripts/make_split.py` เขียน 5 โฟลด์ลง `splits/` โดยซอยเฟรมของแต่ละเซสชันเป็น 5 บล็อกเวลาต่อเนื่อง แล้วเว้น buffer 10 เฟรมรอบบล็อก val เพราะเฟรมติดขอบเกือบเป็นภาพเดียวกัน fold 4 คือบล็อกท้ายของทุกเซสชัน ใกล้เคียงกับวิธีที่ test ถูกตัดออกมามากที่สุด

## 🔪 SAHI คุ้มไหม

คำถามคือควรซอยภาพเป็น tile แล้ว detect ทีละ tile (SAHI) เพื่อให้วัตถุเล็กจับง่ายขึ้นไหม วัดด้วย [`scripts/slice_check.py`](scripts/slice_check.py) ก่อนตอบ

**ย่อทั้งภาพเข้าโมเดล** — ด้านยาวของกล่อง median คือ 78 px บนภาพ 1920 px

| input | สเกล | median หลังย่อ | วัตถุที่เหลือ < 16 px |
|---|---|---|---|
| 640 | 0.33 | 26 px | **30.6%** |
| 800 | 0.42 | 32 px | 22.5% |
| 1280 | 0.67 | 52 px | 6.4% |

ที่ 640 วัตถุเกือบหนึ่งในสามเหลือต่ำกว่า 16 px ซึ่งเล็กกว่า stride ของ backbone ทั่วไป เท่ากับโยนทิ้ง แค่ขยับไป 1280 ก็เหลือ 6.4% แล้ว

**ซอยเป็น tile** — วัตถุอยู่ที่สเกลจริง เหลือแค่ 1.2% ที่ต่ำกว่า 16 px แต่แลกมาด้วยกล่องที่ถูก tile ตัดขาด

| tile | overlap | tiles/ภาพ | กล่องที่ไม่มี tile ไหนครอบได้ทั้งใบ |
|---|---|---|---|
| 512 | 20% | 15 | 10.84% |
| 640 | 20% | 8 | 6.64% |
| 800 | 20% | 6 | 2.92% |
| 960 | 25% | 6 | **1.61%** |

**จุดที่ต้องระวังที่สุด คลาสที่ได้ประโยชน์กับคลาสที่โดนตัด เป็นคนละกลุ่มกัน** (ที่ tile 640)

| class | median px | < 16 px ที่ input 640 | โดน tile ตัดขาด |
|---|--:|--:|--:|
| tuktuk | 42 | **65.6%** | 1.9% |
| bus | 40 | 54.8% | 26.0% |
| motorcycle | 71 | 35.1% | 2.1% |
| car | 82 | 31.1% | 7.6% |
| truck | 115 | 20.5% | 19.0% |
| emergency_car | 350 | 3.2% | **25.8%** |

`tuktuk` กับ `motorcycle` ได้ประโยชน์เต็ม ๆ ส่วน `emergency_car` ตัวใหญ่อยู่แล้ว (median 350 px) การซอยมีแต่ทำให้พัง และเพราะ mAP เฉลี่ยรายคลาส การพัง `emergency_car` เพื่อแลกกับ `tuktuk` คือเจ๊ากันหรือขาดทุน

### สรุป

ใช้ SAHI ได้ แต่ต้องใช้แบบ **sliced + full-image pass แล้วค่อย merge** ตามที่ SAHI ออกแบบมา ให้วัตถุเล็กมาจาก tile และวัตถุใหญ่มาจากภาพเต็ม ไม่ใช่ซอยอย่างเดียว

และมีข้อแลกเปลี่ยนที่ต้องรู้ไว้ — **ขั้นตอน merge ของ SAHI ใช้ NMS/NMM** ซึ่งดึง NMS ที่ตั้งใจจะหนีด้วยการเลือก DETR กลับเข้ามา ข่าวดีคือ NMS ตรงนี้ทำงานกับกล่องซ้ำของวัตถุ *ตัวเดียวกัน* ข้าม tile ซึ่งเป็นเคสที่ง่ายกว่าการแยกรถคนละคันที่จอดบังกันมาก แต่ก็ไม่ใช่ NMS-free อีกต่อไป

ลำดับที่คุ้มที่สุดคือ **ลองดันความละเอียดขาเข้าเป็น 1024–1280 ก่อน** เพราะมันแก้ปัญหาวัตถุเล็กไปได้ 80% ของทาง โดยไม่ต้อง merge อะไรเลยและยังคง NMS-free แล้วค่อยเอา SAHI มาต่อยอดตอน inference ซึ่งไม่ต้องเทรนใหม่ วัดเทียบกันตรง ๆ ได้เลย

## 🧭 แนวทาง

เลือกสาย DETR เพราะทำนายเป็นเซ็ตผ่าน bipartite matching กล่องแต่ละใบจับคู่กับวัตถุหนึ่งตัวตั้งแต่ตอนเทรน จึงไม่ต้องตัดกล่องซ้ำทีหลัง ส่วน **Co-DETR** เพิ่ม auxiliary head แบบ one-to-many ตอนเทรนเพื่อให้ encoder เรียนแน่นขึ้น แล้วทิ้งหัวพวกนั้นตอน inference จึงยังคง NMS-free

### ข้อจำกัดที่ต้องวางแผนรอบ ๆ

- เทรน DETR **from scratch ไม่รอด** ด้วย label 1,605 ภาพ สายนี้กินข้อมูลและ converge ช้า ต้อง fine-tune จาก COCO weights เสมอ ซึ่งได้เปรียบอยู่แล้วเพราะ 6 ใน 11 คลาสตรงกับ COCO
- ที่ไม่ตรงคือ `taxi` `van` `tuktuk` `emergency_car` ซึ่งเป็นการซอย car กับ truck ให้ละเอียดแบบไทย งานส่วนนี้เป็น **classification มากกว่า detection**
- Co-DETR ตัวทางการ ([Sense-X/Co-DETR](https://github.com/Sense-X/Co-DETR)) ผูกกับ MMDetection 2.25.3 / MMCV 1.5.0 / PyTorch 1.11 / Python 3.7 ซึ่งเป็น stack ปี 2022 ทางที่เจ็บน้อยกว่าคือ [`projects/CO-DETR` ใน MMDetection 3.x](https://github.com/open-mmlab/mmdetection/tree/main/projects/CO-DETR) ที่มี checkpoint COCO ให้ fine-tune
- backbone ระดับ Swin-L / ViT-L (304M params) เกินกำลัง GPU 16 GB ถ้าจะเอา Co-DETR จริงต้องเป็น **Co-DINO R50**

## 🚂 เทรน

```bash
uv run python scripts/make_split.py                    # 5 โฟลด์ time-block -> splits/
uv run python scripts/prepare_yolo.py --all            # กางโครง symlink ที่ ultralytics อ่านได้
uv run python scripts/train.py --fold 4 --imgsz 1280   # RT-DETR-l จาก COCO weights
uv run python scripts/predict.py --weights runs/<name>/weights/best.pt
```

**RT-DETR-l ผ่าน ultralytics** เป็น baseline เพราะเป็น DETR family ที่ NMS-free ตามที่ตั้งใจ อ่าน label รูปแบบ YOLO ที่มีอยู่แล้วได้ตรง ๆ และมี COCO weights ให้ fine-tune ซึ่งจำเป็นเพราะมีภาพที่มี label แค่ 1,268 ภาพต่อโฟลด์

การตั้งค่าที่ไม่ใช่ default พร้อมเหตุผล

| ค่า | ตั้งเป็น | ทำไม |
|---|---|---|
| `imgsz` | 1280 | ที่ 640 วัตถุ 30.6% เหลือต่ำกว่า 16 px ที่ 1280 เหลือ 6.4% |
| `batch` | 4 | ใช้ VRAM 11.6 GB จาก 16 GB ที่มี |
| `flipud` · `degrees` | 0 | กล้องนิ่งจับถนน ภาพกลับหัวหรือเอียงแรงไม่มีอยู่จริงใน test |
| `fliplr` | 0.5 | พลิกซ้ายขวาสมเหตุสมผลกับฉากถนน |
| `scale` | 0.3 | default 0.5 ย่อภาพได้ถึง 0.5 เท่า ซึ่งดันวัตถุที่เล็กอยู่แล้วให้ต่ำกว่าเกณฑ์ที่โมเดลมองเห็น |

`predict.py` ตั้ง `conf=0.001` โดยตั้งใจ เพราะ mAP ให้รางวัลกับ recall ที่ precision ต่ำ การตัดกล่องความมั่นใจน้อยทิ้งคือการโยนคะแนนทิ้งเปล่า ๆ
